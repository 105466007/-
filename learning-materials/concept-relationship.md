# 三个概念的关系：Agent、大模型的上下文、Skill

> 本文回答一个问题：**这三个概念是怎么咬合在一起的？**
> 结论先行：**上下文是"工作内存"，Agent 是"在这个内存上循环干活的系统"，Skill 是"按需注入内存的专家知识包"。**

## 一、一句话厘清三者

| 概念 | 角色 | 类比 |
|------|------|------|
| 大模型的上下文（Context） | 系统的**工作内存**：模型一次推理能看到的全部信息 | CPU 的寄存器 / 桌面 |
| Agent | **执行系统**：用"感知→思考→行动→观察"的循环驱动模型完成目标 | 干活的员工 |
| Skill | **知识包**：结构化沉淀的流程与专业知识，按需加载 | 岗位 SOP 手册 |

## 二、上下文如何影响 Agent 的工作

Agent 的每一步决策质量，完全取决于当轮上下文里有什么：

1. **上下文决定 Agent"知道什么"**：任务目标、环境信息、工具返回结果都在上下文里。缺了关键信息，Agent 的"思考"就是无米之炊。
2. **上下文决定 Agent"记得什么"**：Agent 多轮循环靠把历史观察不断拼回上下文。窗口有限，早期信息会被挤出——所以长任务的 Agent 需要摘要压缩、外置笔记（如本仓库的 SKILL.md 索引）。
3. **上下文决定 Agent"像谁"**：系统提示规定角色与边界（如"高风险操作需人工确认"），这直接约束 Agent 的自主性范围。

## 三、Skill 如何补足上下文

没有 Skill 时，Agent 的上下文只有两来源：系统提示（写死的）和对话内容（临时的）。Skill 提供了第三条路——**按需注入的专家知识**：

- **平时不占内存**：只暴露 name + description（几十 token）；
- **触发时精准注入**：任务匹配时，整套"适用场景 / 步骤 / 输出格式 / 质检清单"进入上下文；
- **知识可版本化**：Skill 随 Git 仓库管理，改一次、处处生效。

对比三种"让 Agent 懂行"的方式：

| 方式 | 注入时机 | 适合内容 | 代价 |
|------|----------|----------|------|
| 系统提示 | 每次请求 | 角色与硬规则 | 常驻，占固定 token |
| 对话描述 | 当次对话 | 临时需求 | 每次重复，易遗漏 |
| **Skill** | **任务匹配时** | **可复用的流程与专业知识** | **平时近零，触发时精准** |

## 四、三者协作的全景图

```mermaid
flowchart LR
    U[用户目标] --> A
    subgraph A[Agent 循环]
        P[感知] --> R[思考/规划] --> AC[行动] --> O[观察] --> P
    end
    C[(上下文窗口<br/>工作内存)]
    S[(Skill 库<br/>SOP 手册)]
    R <-- 读上下文决策 --> C
    O <-- 写入观察结果 --> C
    R -. 任务匹配 description .-> S
    S -. 加载 SKILL.md 正文 .-> C
```

读图要点：

- **上下文在中间**：Agent 的"思考"读它，"观察"写它——它是整个循环的信息枢纽；
- **Skill 在旁边**：不直接参与循环，而是在"思考"环节发现任务匹配时，把专业知识**注入上下文**，相当于给员工临时发一本手册；
- **循环在左**：Agent 的自主性来自这个循环，但每次"思考"的质量都被当时的上下文内容框定。
