核心概念

一句话定义：上下文（Context）是大模型在一次推理中能看到的所有信息——包括系统提示、全部对话历史、检索到的资料和工具返回结果；它能容纳的信息总量上限就是上下文窗口（Context Window），以 token 计量。
💡 类比：上下文像一张"只能放在桌面上的办公桌"。模型工作时只能看桌上的文件：桌面就是上下文窗口，桌面大小就是窗口上限。桌下（训练数据）的东西它"学过"但看不见；想用就得把文件重新拿上来（放进上下文）。

机制原理

1. 上下文里装了什么？

  1. Token 化：所有文本先被切分成 token（词元）。窗口大小按 token 计：中文约 1 字 ≈ 1~2 token。超窗内容无法被本次推理看到。
  2. 注意力分配：模型通过注意力机制"阅读"上下文。研究表明存在 lost in the middle：开头和结尾的信息利用得好，埋在中间的长内容容易被忽略。
  3. 无状态：模型本身不记得上一次请求——所谓的"多轮记忆"是把历史对话重新放进上下文实现的。会话结束、或你开新窗口，上下文即消失。
  4. 上下文工程：因为窗口有限、注意力有限，"往上下文里放什么、放多少、按什么顺序放"成为一种工程方法：压缩历史、摘要替代全文、检索相关片段（RAG）、把长期知识外置成文件按需读取。
✅ 为什么重要：模型回答质量的上限，很大程度上由"上下文里有没有正确的信息"决定。它不知道的事，放不进上下文它就答不了。

应用场景：长对话的上下文压缩

在一个持续三小时的技术排障会话里，对话历史已积累 8 万 token，接近窗口上限，响应开始变慢、早期细节被"挤出"。

做法效果
把前两小时的内容压缩成 500 token 的摘要（关键结论 + 已尝试方案）腾出窗口空间，关键信息保留
把完整的排查记录写入一个 notes.md 文件细节不丢失，需要时按需读回
系统提示固定不动（角色、规则不变）保持行为一致

这就是"上下文工程"的典型操作：不是被动地等窗口被塞满，而是主动管理"桌上放什么"。

常见误区与辨析

误区正确理解
上下文 = 模型的记忆，聊过它就一直记得 上下文只在单次推理中存在。"记得"靠的是每次把历史重新放入上下文。跨会话的持久记忆需要外部存储（文件、数据库）配合检索。
窗口越大，模型记得越牢 窗口大只保证"放得下"，不保证"看得重"。由于 lost in the middle，塞满超长上下文反而可能漏掉关键信息。有效利用靠筛选和组织，而非硬塞。
加大上下文可以替代微调 两者解决不同问题。上下文注入"临时知识"（这篇文档说了什么），微调改变"固有能力与风格"（始终按某格式输出）。频繁使用、体量巨大的稳定知识适合微调/训练；每次不同的动态信息适合上下文。

自测题

Q1：列出一次典型 LLM API 请求中上下文的四个组成部分。

参考答案：系统提示（角色与规则）、对话历史（此前所有轮次）、检索内容（RAG 注入的资料）、工具返回结果。

漏项说明：漏掉"工具结果"或"检索内容"，说明还把大模型当成"纯聊天"，回到「机制原理」第 1 点。

Q2：为什么"上下文窗口 200K token"不等于"模型能可靠利用 200K token 的信息"？

参考答案：窗口是容量上限，但注意力分配不均匀，存在 lost in the middle：埋在中间的信息召回率明显低于开头和结尾。所以长上下文需要配合摘要、结构化、关键信息前置等手段，而不是无脑堆料。

Q3：你想让模型永远记住你公司的产品手册（300 页，内容基本不变），应该用上下文还是微调/知识库？为什么？

参考答案：用知识库 + 检索（RAG）：手册体量远超任何窗口，且内容稳定但查询各异——把相关章节检索后注入上下文最经济。微调不适合频繁更新的文档知识；全量塞上下文既贵又受 lost in the middle 影响。

Q4：新开一个对话窗口，模型"忘了"上次说过的所有内容。请解释原因并给出一种低成本解决办法。

参考答案：模型无状态，上次的上下文没有随请求传入。低成本办法：把上次的关键结论写成一段摘要/笔记文件，新会话开始时粘贴或读入——即"用外部文件持久化 + 按需注入上下文"。
