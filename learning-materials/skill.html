核心概念

一句话定义：Skill 是一个以 SKILL.md（含 YAML 元数据）为核心、可附带脚本与资源文件的知识/流程打包格式——把"某类任务该怎么做"写成结构化文档，让 AI 在需要时自动发现并加载，按里面的流程执行。
💡 类比：Skill 像"岗位 SOP 手册"。新员工（模型）通用能力很强，但你公司报销怎么走、周报用什么格式，它不知道。把流程写成手册放进柜子（skills 目录），并在目录索引上写清"什么情况翻这本"（description），员工遇到对应任务就会取出来照着做。

关键词

SKILL.mdYAML frontmatter按需加载渐进式披露流程沉淀可复用

机制原理

  1. 打包：每个 Skill 是一个文件夹，核心是 SKILL.md：头部 YAML 写 name（唯一名称）和 description（何时使用），正文写适用场景、输入、步骤、输出结构、约束、质检要求。可附带脚本、模板等资源。
  2. 发现：AI 助手启动时不读取全部正文，只读每个 Skill 的 name + description——相当于只看"书脊"。这保证 Skill 多了也不会撑爆上下文。
  3. 触发：用户请求与某个 description 匹配时（如"帮我做周报"匹配上周报 Skill），该 Skill 的正文才被完整加载进上下文。
  4. 执行：模型按正文的步骤、约束和输出格式执行任务；引用的脚本/资源文件按需读取。
  5. 两级存放：用户级（~/.workbuddy/skills/，跨项目可用）；项目级（<仓库>/.workbuddy/skills/，随仓库共享给团队）——本仓库用的就是项目级。
✅ 渐进式披露（Progressive Disclosure）是灵魂：平时只占几十 token 的索引，任务到来时才加载全文。既让专业知识"随叫随到"，又不浪费上下文预算。

应用场景：把"周报格式"沉淀成 Skill

没有 Skill 时：每周写周报都要重新描述格式、口径、要包含的项目——说漏一次就返工一次。

步骤操作
① 沉淀写 weekly-report/SKILL.md：description 写"当用户要求写/整理周报时使用"；正文定义输入（本周事项列表）、步骤（按项目分组→标注进度与风险→生成表格）、输出结构、质检项（数字必须来自用户提供的原始记录）
② 使用以后只需说"帮我写这周的周报，事项如下：……"，Skill 自动触发
③ 迭代发现漏了"下周计划"栏目？直接改 SKILL.md——一次修改，永久生效

本质：把"每次都要口头交代"的个人经验，变成"一次编写、持续复用、随仓库共享"的组织资产。

常见误区与辨析

误区正确理解
Skill 就是一段高级提示词 提示词是"当次对话有效"；Skill 是结构化、持久化、可被发现和复用的资产——有元数据索引、有固定的质量约束（frontmatter 合法性、质检清单），还能附带可执行脚本，且可以随 Git 仓库版本管理与共享。
Skill = 插件 / MCP MCP 连接外部系统提供"能力"（调 API、查数据库）；Skill 提供"知识与流程"（怎么做好某类任务）。Skill 纯文档也能生效，不需要任何外部服务；二者常配合使用——MCP 给工具，Skill 教用法。
Skill 写完就一定会被触发 触发靠 description 匹配。description 含糊（如"很有用的助手"）→ 永远不触发；清晰写出触发场景和关键词 → 才能在正确时机被选中。写完必须实测。

自测题

Q1：写出 SKILL.md 头部必须包含的两个 YAML 字段，并说明各自作用。

参考答案：name：Skill 的唯一名称，用于索引和调用；description：描述"这个 Skill 是干什么的、什么时候该用它"，是触发匹配的唯一依据。

答错说明：如果只答了 name，说明忽略了"发现机制"依赖 description——回到「机制原理」第 2、3 步。

Q2：为什么 Skill 正文平时不加载、只在触发时加载？这种设计叫什么？

参考答案：叫渐进式披露 / 按需加载。平时只读 name+description（几十 token），保护有限的上下文窗口；触发后才加载全文执行。若全部常驻，Skill 一多上下文就会被指令淹没，挤压真正的工作内容。

Q3：你想让 AI 每次都按团队规范做代码评审。提示词、Skill、MCP 三种方案怎么选？

参考答案：选 Skill：评审规范是"知识+流程"（检查清单、输出格式），需要持久化、可复用、随仓库共享——正是 Skill 的形态。提示词每次粘贴不可持续；MCP 适合"需要连接外部系统"的场景（如拉取 PR diff 的工具），与规范本身互补但不互替。

Q4：一个 Skill 从未被触发过，最可能的原因是什么？如何排查？

参考答案：大概率是 description 写得含糊或与用户表述不匹配。排查：① 对照用户的实际说法检查 description 是否含对应关键词/场景；② 直接点名 Skill 测试能否加载；③ 修改 description 后重新实测。
